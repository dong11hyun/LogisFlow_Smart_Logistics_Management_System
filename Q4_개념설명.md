# Q4 이력 조회 최적화 방안 - 개념 설명

> **문제**: 500억 건의 `shipment_updates` 테이블에서 특정 화물의 상태 변경 이력(타임라인)을 빠르게 조회하려면?

---

## 📋 방안 비교 요약

| 방안 | 저장소 | Server Avg (1억) | 스케일 확장성 | 복잡도 |
|:----:|:------:|:----------------:|:-------------:|:------:|
| **방안 1** | PostgreSQL (파티션) | 44.79ms | 중간 | 낮음 |
| **방안 2** | Elasticsearch | 74.52ms | 높음 | 높음 |

```
┌─────────────────────────────────────────────────────────────────┐

│                                                                 │
```


### 코드 구현

**SQL 스키마 (schema/04_partitioned_schema.sql)**

```sql
-- 1. 부모 테이블 정의 (파티션 키: timestamp)
CREATE TABLE shipment_updates (
    update_id BIGSERIAL,
    shipment_id INT NOT NULL,
    status_code VARCHAR(50) NOT NULL,
    notes TEXT,
    timestamp TIMESTAMP NOT NULL,
    PRIMARY KEY (update_id, timestamp)  -- 파티션 키 포함 필수
) PARTITION BY RANGE (timestamp);

-- 2. 월별 파티션 생성 (36개: 2024.01 ~ 2026.12)
CREATE TABLE shipment_updates_2024_01 
    PARTITION OF shipment_updates
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE shipment_updates_2024_02 
    PARTITION OF shipment_updates
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- ... (36개 반복)

CREATE TABLE shipment_updates_2026_12 
    PARTITION OF shipment_updates
    FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');

-- 3. 복합 인덱스 (각 파티션에 자동 적용)
CREATE INDEX idx_updates_shipment_ts 
    ON shipment_updates (shipment_id, timestamp DESC);
```

**Python API (조회)**

```python
async def get_timeline(shipment_id: int, db: Session):
    """타임라인 조회 - 파티션 프루닝 자동 적용"""
    
    updates = db.query(ShipmentUpdate)\
        .filter(ShipmentUpdate.shipment_id == shipment_id)\
        .order_by(ShipmentUpdate.timestamp.desc())\
        .all()
    
    return updates
```

### 장단점

| 장점 | 단점 |
|:----:|:----:|
| ✅ 기존 인프라 활용 (추가 비용 없음) | ❌ 단일 DB 부하 집중 |
| ✅ SQL 그대로 사용 가능 | ❌ 수평 확장(Scale-Out) 어려움 |
| ✅ 파티션 단위 삭제/아카이빙 용이 | ❌ 파티션 관리 필요 |
| ✅ 트랜잭션 ACID 보장 | ❌ 10억 건+ 시 한계 |

```python
async def index_status_update(update_id, shipment_id, status_code, notes, timestamp):
    """Elasticsearch에 문서 인덱싱"""
    
    doc = {
        "update_id": update_id,
        "shipment_id": shipment_id,
        "status_code": status_code,
        "notes": notes,
        "timestamp": timestamp
    }
    
    response = requests.post(
        f"{ES_URL}/shipment-updates/_doc/{update_id}",

    )
    return response.json()
```

**타임라인 조회 (routers/shipments.py)**

```python
async def get_timeline_from_es(shipment_id: int):
    """Elasticsearch에서 타임라인 조회"""
    
    query = {
        "query": {
            "term": {"shipment_id": shipment_id}
        },
        "sort": [{"timestamp": "desc"}]
    }
    
    response = requests.post(
        f"{ES_URL}/shipment-updates/_search",
        json=query
    )
    
    return response.json()["hits"]["hits"]
```

## 📊 벤치마크 결과

> **비교 기준:** Server Avg Time (순수 서버 조회 시간)

| 규모 | PostgreSQL | Elasticsearch | 승자 (개선율) | 트리거 | 생성기 |
|:----:|:----------:|:-------------:|:-------------:|:------:|:------:|
| **300만 건** | **24.51ms** | 72.51ms | PostgreSQL (66%↑) | ✅ 활성화 | Faker 사용 |
| **3,000만 건** | **21.46ms** | 63.81ms | PostgreSQL (66%↑) | ❌ 비활성화 | Faker 제거 |
| **1억 건** | **44.79ms** | 74.52ms | PostgreSQL (40%↑) | ❌ 비활성화 | Faker 제거 |

### 성능 변화 분석

```
📊 규모 증가에 따른 성능 변화

PostgreSQL (파티션 테이블):
   300만 → 1억 (33배 증가)
   24.51ms → 44.79ms (83% 느려짐)
   → 파티션 프루닝 덕분에 선형 증가 수준으로 억제됨

Elasticsearch:
   300만 → 1억 (33배 증가)
   72.51ms → 74.52ms (거의 동일!)
   → 분산 아키텍처 덕분에 스케일에 강함
```

## ⚠️ 저장소 선택 가이드

| 상황 | 추천 저장소 | 이유 |
|:----:|:-----------:|:-----|
| **~10억 건, 단순 ID 조회** | PostgreSQL | 파티션 프루닝 + 인덱스 효과 |
| **10억 건+, 분산 필요** | Elasticsearch | 스케일 증가에도 일정한 성능 |
| **풀텍스트 검색** | Elasticsearch | 역인덱스 특화 |
| **복합 필터링/집계** | Elasticsearch | 강력한 쿼리 DSL |
| **트랜잭션 필요** | PostgreSQL | ACID 보장 |
| **인프라 단순화** | PostgreSQL | 추가 시스템 불필요 |
