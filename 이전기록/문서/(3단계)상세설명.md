## 3-2: 모델/스키마/라우터 구현

###  models.py - SQLAlchemy 모델

DB 테이블과 1:1 매핑되는 ORM 모델

```python
class Shipment(Base):
    """화물 모델 (비정규화 컬럼 포함)"""
    __tablename__ = "shipments"
    
    # 기본 컬럼
    shipment_id = Column(Integer, primary_key=True)
    company_id = Column(Integer, ForeignKey("companies.company_id"))
    origin_warehouse_id = Column(Integer)
    destination_warehouse_id = Column(Integer)
    created_at = Column(DateTime)
    
    # ★ 비정규화 컬럼 (Q2 답변 구현)
    current_status = Column(String(50))           # 현재 상태
    last_updated_at = Column(DateTime)            # 마지막 업데이트
    origin_warehouse_name = Column(String(100))   # 출발 창고명
    destination_warehouse_name = Column(String(100))  # 도착 창고명


class ShipmentUpdate(Base):
    """상태 변경 로그 (파티션 테이블)"""
    __tablename__ = "shipment_updates"
    
    update_id = Column(BigInteger, primary_key=True)
    shipment_id = Column(Integer)
    status_code = Column(String(50))
    notes = Column(String(255))
    timestamp = Column(DateTime)
```

###  schemas.py - Pydantic 스키마

API 요청/응답 데이터 검증

```python
class StatusCode(str, Enum):
    """상태 코드 Enum"""
    PENDING = "PENDING"
    PICKED_UP = "PICKED_UP"
    IN_TRANSIT = "IN_TRANSIT"
    OUT_DELIVERY = "OUT_DELIVERY"
    DELIVERED = "DELIVERED"


class StatusUpdateRequest(BaseModel):
    """상태 변경 요청 (Q3 테스트용)"""
    status_code: StatusCode
    notes: Optional[str]
    strategy: Optional[str] = "sync"  # sync, trigger, async


class StatusUpdateResponse(BaseModel):
    """상태 변경 응답"""
    update_id: int
    shipment_id: int
    status_code: str
    timestamp: datetime
    processing_time_ms: float  # ★ 성능 측정용
    strategy_used: str         # ★ 사용된 전략


class TimelineResponse(BaseModel):
    """타임라인 조회 응답 (Q4 테스트용)"""
    shipment_id: int
    timeline: List[TimelineEntry]
    query_time_ms: float       # ★ 성능 측정용
    source: str                # ★ postgresql 또는 elasticsearch
```

## 3-3: 상태 변경 API (Q3용) 

###  엔드포인트

```
POST /shipments/{shipment_id}/status
```

###  목적

Q3의 3가지 정합성 전략을 **하나의 API에서 테스트**

###  요청/응답 예시

```json
// 요청
POST /shipments/12345/status
{
    "status_code": "DELIVERED",
    "notes": "배송 완료",
    "strategy": "sync"    // ← 전략 선택!
}

// 응답
{
    "update_id": 999999,
    "shipment_id": 12345,
    "status_code": "DELIVERED",
    "timestamp": "2026-01-11T14:00:00",
    "processing_time_ms": 15.32,  // ← 성능 측정!
    "strategy_used": "sync"
}
```

###  현재 구현된 전략

```python
if strategy == "sync":
    # =============================================
    # 전략 1: 동기 트랜잭션
    # 하나의 트랜잭션에서 INSERT + UPDATE 모두 수행
    # =============================================
    
    # 1. 상태 로그 INSERT
    new_update = ShipmentUpdate(
        shipment_id=shipment_id,
        status_code=request.status_code,
        notes=request.notes
    )
    db.add(new_update)
    
    # 2. 비정규화 컬럼 동기화 UPDATE
    shipment.current_status = request.status_code
    shipment.last_updated_at = new_update.timestamp
    
    # 3. 커밋 (원자적 트랜잭션)
    db.commit()

elif strategy == "trigger":
    # TODO: 4단계에서 구현
    raise HTTPException(501, "아직 구현되지 않음")

elif strategy == "async":
    # TODO: 4단계에서 구현
    raise HTTPException(501, "아직 구현되지 않음")
```

###  Q3 전략 비교 포인트

| 전략 | 구현 방식 | 장점 | 단점 |
|------|-----------|------|------|
| sync | 앱 트랜잭션 | 강한 일관성 | 응답 느림 |
| trigger | DB 트리거 | 앱 코드 단순 | DB 부하 |
| async | Kafka | 빠른 응답 | 지연 일관성 |

## 3-4: 타임라인 조회 API (Q4용) 

###  엔드포인트

```
GET /shipments/{shipment_id}/timeline?source=postgresql
```

###  목적

Q4의 2가지 저장소 방안을 **하나의 API에서 테스트**

###  요청/응답 예시

```json
// 요청
GET /shipments/12345/timeline?source=postgresql

// 응답
{
    "shipment_id": 12345,
    "current_status": "DELIVERED",
    "timeline": [
        {"update_id": 999999, "status_code": "DELIVERED", "timestamp": "2026-01-11T14:00:00"},
        {"update_id": 999998, "status_code": "OUT_DELIVERY", "timestamp": "2026-01-11T12:00:00"},
        {"update_id": 999997, "status_code": "IN_TRANSIT", "timestamp": "2026-01-11T08:00:00"},
        {"update_id": 999996, "status_code": "PICKED_UP", "timestamp": "2026-01-10T16:00:00"},
        {"update_id": 999995, "status_code": "PENDING", "timestamp": "2026-01-10T10:00:00"}
    ],
    "total_updates": 5,
    "query_time_ms": 3.21,      // ← 성능 측정!
    "source": "postgresql"
}
```

###  현재 구현된 방안

```python
if source == "postgresql":
    # =============================================
    # 방안 1: PostgreSQL 파티션 테이블에서 조회

    updates = db.query(ShipmentUpdate)\
        .filter(ShipmentUpdate.shipment_id == shipment_id)\
        .order_by(desc(ShipmentUpdate.timestamp))\
        .all()
    
    # 파티션 프루닝 덕분에 해당 월 파티션만 스캔!

elif source == "elasticsearch":
    # TODO: 5단계에서 구현
    raise HTTPException(501, "아직 구현되지 않음")
```

###  Q4 방안 비교 포인트

| 방안 | 데이터 소스 | 장점 | 단점 |
|------|-------------|------|------|
| postgresql | 파티션 테이블 | 강한 일관성 | 대용량 시 느림 |
| elasticsearch | ES 인덱스 | 빠른 검색 | 동기화 필요 |

## 💡 핵심 포인트

| 항목 | 설명 |
|------|------|
| **진입점** | 모든 테스트가 API를 통해 진행 |
| **전략 스위치** | `strategy`, `source` 파라미터로 전략 선택 |
| **성능 측정** | 응답에 `processing_time_ms`, `query_time_ms` 포함 |
| **문서화** | `/docs`에서 Swagger UI로 쉽게 테스트 |

- **API가 없으면** → 각 전략을 개별 스크립트로 만들어야 함 (복잡)
- **API가 있으면** → 하나의 엔드포인트에서 전략만 바꿔가며 테스트 가능 (깔끔)

```
Q3 정합성 전략:
├── 전략 1: 동기 트랜잭션 ✅ 구현됨
├── 전략 2: DB 트리거    ❌ 아직
└── 전략 3: Kafka 비동기  ❌ 아직
Q4 저장소 비교:
├── 방안 1: PostgreSQL 파티션 ✅ 구현됨
└── 방안 2: Elasticsearch     ❌ 아직
```
